# subagent-catalog

A Claude Code skill for browsing and fetching subagents from the [awesome-claude-code-subagents](https://github.com/VoltAgent/awesome-claude-code-subagents) catalog.

## Installation

Copy the `subagent-catalog/` folder to `~/.claude/commands/`:

```bash
cp -r tools/subagent-catalog ~/.claude/commands/
```

## Usage

| Command | Description |
|---------|-------------|
| `/subagent-catalog:search <query>` | Find agents by name, description, or category |
| `/subagent-catalog:fetch <name>` | Get full agent definition |
| `/subagent-catalog:list` | Browse all categories |
| `/subagent-catalog:invalidate` | Clear cache (add `--fetch` to refresh immediately) |

## Examples

**Find security-related agents:**
```
/subagent-catalog:search security
```

**Get the code-reviewer definition:**
```
/subagent-catalog:fetch code-reviewer
```

**Browse all available agents:**
```
/subagent-catalog:list
```

## Features

- **Smart caching**: 12-hour TTL with graceful fallback on network failure
- **Atomic updates**: Uses tmp file + mv pattern to prevent partial writes
- **Cross-platform**: Works on macOS and Linux
- **Best practices**: Follows Anthropic skill authoring guidelines

## Cache

- **Location**: `~/.claude/cache/subagent-catalog.md`
- **TTL**: 12 hours (configurable in `config.sh`)
- **Behavior**: Auto-refreshes when stale, falls back to old cache on network failure

## Troubleshooting

| Issue | Fix |
|-------|-----|
| Stale results | `/subagent-catalog:invalidate --fetch` |
| Network error | Check connection, retry |
| Agent not found | `/subagent-catalog:search <partial-name>` first |

## Supply-chain integrity (AO-10)

Two separate things in this repo pull from
[VoltAgent/awesome-claude-code-subagents](https://github.com/VoltAgent/awesome-claude-code-subagents),
and they're protected two different ways because they carry different risk:

1. **This tool** (`search`/`fetch`/`list`/`invalidate`) fetches live, at the
   time a user runs a command, via `curl` in `config.sh`. That fetch is now
   pinned to a commit SHA (`SUBAGENT_CATALOG_COMMIT` in `config.sh`) instead of
   `main`, so it always returns bytes that were reviewed when the pin was last
   moved, not whatever landed upstream since. See the comment above
   `SUBAGENT_CATALOG_COMMIT` in `config.sh` for how to bump it.

2. **The `categories/` directory** at the repo root is a *vendored copy* of
   the same catalog, committed to this repo and loaded by
   `packages/server/src/registry` as the real agent registry: every file's
   body becomes a system prompt verbatim, and its `tools:` frontmatter becomes
   the tool-access grant the provider layer enforces. Because it's committed
   rather than fetched at runtime, a change to it goes through normal PR
   review — but a `tools:` line gaining `Bash` inside a 150-line prose diff is
   easy for a reviewer to miss; it reads as a docs change, not a privilege
   change.

   `catalog-manifest.yaml` in this directory is a per-file SHA-256 manifest of
   every agent file under `categories/`, generated by
   `packages/server/src/scripts/verifyCatalogManifest.ts generate`. CI runs
   `verifyCatalogManifest.ts verify` on every push and PR (see
   `.github/workflows/ci.yml`), which fails loudly if any vendored file's hash
   no longer matches the manifest, *and* prints a tool-grant delta — the
   manifest's recorded `tools:` list for a file versus what's actually in the
   working tree right now — so an escalation shows up as its own labelled
   section in the CI log instead of hiding inside a markdown diff. See the
   header comment in `verifyCatalogManifest.ts` for the full design rationale.

   Whenever `categories/` is intentionally refreshed from upstream, regenerate
   the manifest in the same commit (`generate`, then `verify` to confirm it's
   clean) and read the delta report before merging — that report is the actual
   control this finding asks for; the hashes only prove *something* changed.
